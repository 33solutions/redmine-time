# Redmine: аналитик, учёт времени и контроль задач

Скилл работает не как транспорт «текст → API», а как аналитик: формулирует описания и комментарии по редакционному стандарту, разбирает крупную работу на дерево подзадач, проверяет каждый уходящий текст на компрометацию и никогда ничего не отправляет без явного подтверждения пользователя.

```bash
bun ~/.claude/skills/redmine-time/scripts/redmine.ts <команда> [флаги]
```

`... help` — полный список команд. Инстансы, их адреса и разметка описаний берутся из `~/.redmine/config.json`: имена профилей видно командой `... instances`.

## Железные правила

1. **Ничего не отправляется без подтверждения.** Команды `log`, `batch`, `comment`, `create-issue`, `create-tree`, `update-issue`, `edit`, `create-project`, `update-project`, `archive-project`, `relate`, `unrelate` без `--yes` печатают полный предпросмотр и выходят. Порядок всегда один: собрать текст → прогнать команду без `--yes` → показать пользователю **целиком, дословно, со всеми текстами** → получить «да» → повторить с `--yes`. На вопрос отвечай формулой «отправить или скорректировать?».
2. **Предпросмотр не сокращается.** Пользователь должен увидеть ровно тот текст, который уйдёт заказчику, включая разметку. Не пересказывай его своими словами.
3. **Проверка на компрометацию — до показа.** Если сканер остановил отправку, текст правится, а не обходится. `--override-guard` применяется только по явной просьбе пользователя, и об этом говорится вслух.
4. **Тексты — по стандарту**, а не «как сказал пользователь». Пользователь даёт суть, скилл пишет документ: см. `references/editorial.md`. Черновую формулировку пользователя показывай уже переработанной.
5. **Удаление** (`delete`) требует `--yes` и отдельного подтверждения, даже если пользователь только что согласился на другую операцию.
6. **Инцидент описывается по отдельному стандарту.** Любой текст про сбой, взлом, утечку или простой пишется по разделу «Тексты об инцидентах» в `references/editorial.md`: сухая хронология с датами, что сделано, как проверено — без обязанностей и надзорных органов, без распределения вины, без подробностей атаки. Утверждение о мире всегда заменяется утверждением о наблюдении. Проверка на юридическую чистоту обязательна; `--override-guard` на этих правилах применяется только по явной устной просьбе пользователя, и об этом говорится вслух.

## Роль аналитика

Когда пользователь говорит «заведи задачу», «опиши», «прокомментируй», «разбери на подзадачи» — он даёт исходные данные, а не готовый текст. Работа скилла:

1. **Достроить контекст.** Прочитать смежные задачи (`issue`, `issues --subject`, `search`), понять проект, увидеть, как оформлены соседние задачи.
2. **Спросить недостающее — коротко и по делу.** Не более 2–3 вопросов, и только то, без чего текст будет неверным: результат, срок, ответственный, что считается приёмкой. Остальное — разумные допущения, которые явно помечены в тексте как допущения.
3. **Написать документ** по структуре из `references/editorial.md`: что делаем → зачем → объём → критерии приёмки → ограничения → что требуется от заказчика с датами → связи.
4. **Проставить связи.** Ссылки на родителя, на смежные задачи, на предыдущие комментарии по смыслу. Связь без номера или адреса — не связь. Задача того же инстанса пишется номером `#NNNN`; задача другого инстанса — только полным адресом с названием проекта, потому что `#NNNN` там указывает на чужую задачу (`xref` печатает готовую строку). Зависимость между задачами одного инстанса выражается связью Redmine (`relate`), а не фразой в тексте. Правило целиком — `references/editorial.md`, раздел «Ссылки между задачами».
5. **Показать и согласовать.**

Комментарий строится так же: сделано → как проверить → что это даёт → дальше → что требуется от адресата (с именем роли и датой). Шаблоны и таблица «вместо → пишем» — в `references/editorial.md`.

## Декомпозиция задачи на дерево

Пользователь формулирует работу одной фразой — скилл предлагает дерево.

1. Уточнить результат, срок и ответственного (не больше трёх вопросов).
2. Разрезать по **проверяемым результатам**, а не по действиям. Размер подзадачи — 2–16 часов; первым этапом идёт обследование, если объём неизвестен.
3. Написать шапку родителя (цель, состав работ таблицей, контрольные точки, условия срока — **без дублирования цифр подзадач**: Redmine агрегирует оценку, списанное и готовность сам) и описания подзадач.
4. Сложить план в JSON, описания — отдельными HTML-файлами во временной папке.
5. Показать предпросмотр дерева целиком (`create-tree` без `--yes` печатает родителя и каждую подзадачу с текстами), получить согласие, создать с `--yes`.
6. После создания показать `tree <id>` — дерево с агрегатами.

```bash
... create-tree --file /tmp/plan.json --instance ru            # предпросмотр
... create-tree --file /tmp/plan.json --instance ru --yes      # создание
... tree 25127 --instance ru                                   # агрегаты по дереву
```

Формат плана и правила разреза — `references/editorial.md`.

## Связи между задачами

Иерархия отвечает на вопрос «из чего состоит работа», связь — на вопрос «что от чего зависит». Это разные вещи, и путать их не надо: `tree` показывает состав, `relations` — зависимости.

```bash
... relations 25185 --instance ru                                  # связи задачи словами
... relate 25194 --to 25197 --type blocks --instance ru            # предпросмотр
... relate 25194 --to 25197 --type blocks --instance ru --yes      # создание
... relate 25194 --to 25197 --type precedes --delay 2 --instance ru
... unrelate 812 --instance ru --yes                               # удалить связь
```

Типы Redmine: `relates`, `duplicates`, `duplicated`, `blocks`, `blocked`, `precedes`, `follows`, `copied_to`, `copied_from`. Принимаются и русские названия: «связана», «дублирует», «дублируется», «блокирует», «заблокирована», «предшествует», «следует».

1. **Подтверждение как везде.** Без `--yes` печатается предпросмотр: обе задачи с темами, статусами и сроками, тип связи и что он означает словами — «#25194 блокирует #25197: пока #25194 не закрыта, #25197 выполнять нельзя». Показывай этот текст пользователю целиком: человек соглашается на смысл, а не на код типа.
2. **Связь — это поведение, а не пометка.** `blocks` не даст закрыть заблокированную задачу, `precedes` сдвинет даты второй задачи при переносе первой, `duplicates` закроет дубль вместе с оригиналом. Предупреждай об этом до подтверждения — особенно о сдвиге дат.
3. **Проверка до отправки.** Скилл убеждается, что обе задачи существуют и доступны, что это не одна и та же задача и что связи между ними ещё нет. Отказ `422` разворачивается в объяснение: цикл в порядке выполнения, связь с собственной подзадачей, уже существующая связь. Не показывай пользователю код ответа — показывай причину.
4. **`--delay` только для `precedes` и `follows`.** В остальных типах отсрочка ничего не значит, и команда об этом скажет.
5. **Смысловая зависимость выражается связью, а не фразой в тексте.** «Ждём, пока доделают соседнюю задачу» — это `blocked` с номером; Redmine тогда следит за порядком сам.

## Два инстанса: перекрёстные ссылки

**Связей Redmine между инстансами не бывает** — ни через API, ни через интерфейс. У второго Redmine своя нумерация, и объекта, который связал бы две базы, не существует. Говори это прямо и не пытайся обойти.

Между инстансами связь — это ссылка в тексте обеих задач:

```bash
... xref 25185 --instance ru      # готовая строка для вставки в текст на другом инстансе
```

Команда печатает `<a href="https://…/issues/25185">33 Решения #25185 — Панель контроля менеджеров…</a>`: адрес, название проекта и тема. Разметка берётся от инстанса, куда строка пойдёт (`--markup` переопределяет).

1. **Номер без адреса на другом инстансе — ошибка.** `#25185` там указывает на чужую задачу и ведёт читателя не туда. Ошибка делается за секунду, а замечают её через месяцы. Правило целиком — `references/editorial.md`, раздел «Ссылки между задачами».
2. **Ссылка нужна с обеих сторон.** Задача на разработку называет задачу внедрения у клиента, задача внедрения — задачу на разработку. Односторонняя ссылка бесполезна.
3. **`relate` с задачей другого инстанса ничего не создаёт**: команда объясняет, почему связи не будет, и печатает готовую перекрёстную ссылку. Вставляется она обычным путём — `comment` или `update-issue` с подтверждением.
4. **В карточке задачи такие ссылки видно отдельно.** `issue` и `relations` собирают из описания и комментариев ссылки на второй инстанс и показывают их блоком «Связано на другом инстансе» — чтобы единственная имеющаяся связь не терялась в тексте.

## Проекты и подпроекты

Проект — контейнер работы: у него свои участники, трекеры, модули и отчётность. Заводить его чаще приходится под нового клиента или под обособленное направление у действующего; всё остальное — подпроект.

```bash
... projects --instance ru                      # дерево: родитель → подпроекты
... projects "пример" --instance ru             # фильтр; родители показываются для контекста
... create-project --instance ru --name "Пример: обмен с маркетплейсами" \
      --parent primer --description-file /tmp/project.html \
      --tracker "Разработка" --tracker "Поддержка 1С" \
      --module issue_tracking --module time_tracking          # предпросмотр
... create-project --instance ru --name "…" --parent primer --description-file /tmp/project.html --yes
... project-fields --instance ru                 # пользовательские поля проектов: номер, значения
... create-project --instance ru --name "…" --field "Статус=Контроль" --field "12=1"
... update-project primer-marketpleysy --instance ru --name "Пример: маркетплейсы" --parent none
... archive-project <identifier> --instance ru --yes
```

Порядок работы:

1. **Сначала решить: проект или подпроект.** Отдельный проект нужен, когда у работы свой заказчик, свой договор и своя отчётность. Направление внутри действующего клиента — подпроект: `--parent <identifier|id>`. Посмотреть, куда встраиваться, — `projects` деревом.
2. **Идентификатор.** Без `--identifier` он генерируется из названия транслитерацией: строчная латиница, цифры, дефис и подчёркивание, не длиннее 100 символов. Правило то же, что у самого Redmine: цифра в начале допустима («33 Решения» → `33-resheniya`), запрещён только идентификатор из одних цифр. Скилл проверяет занятость **до отправки** — в том числе идентификаторы невидимых (закрытых и архивированных) проектов.
3. **Описание — документ, а не строка.** Что это за проект, границы (что в нём ведётся, а что нет), как ведём работу. Шаблон — в `references/editorial.md`, раздел «Описание проекта». Текст передавать файлом: `--description-file`.
4. **Публичность — осознанное решение.** Без флагов проект создаётся **закрытым**; `--public` делает его видимым всем, у кого есть учётная запись. Для клиентских проектов публичность почти всегда ошибка — предупреждай об этом до подтверждения.
5. **Трекеры и модули зависят от инстанса.** Несуществующее имя останавливает команду до отправки и печатает список доступного. Модули опознаются техническим именем (`issue_tracking`, `time_tracking`, `wiki`). Справочники: `... trackers`, `... projects --json`.
6. **Пользовательские поля проекта.** На инстансе они бывают обязательными — без них создание отклоняется с `422`. Посмотреть набор: `... project-fields`. Задать: `--field "Статус=Контроль"`, флаг повторяется, вместо имени допустим номер (`--field "12=1"`). Имя разворачивается в номер **до** отправки: неизвестное поле останавливает команду и печатает список доступных. Справочник `custom_fields.json` отдаётся только администратору; без прав скилл собирает имена, номера и встречавшиеся значения из карточек видимых проектов, а полный список значений и обязательность берутся из формы создания проекта в интерфейсе.
7. **Права.** Создание проекта требует прав администратора либо роли с разрешением «Создание проекта»; подпроект — разрешения «Создание подпроектов» в родительском проекте. Отказ `403` скилл разворачивает в объяснение: чего не хватает и что делать. Не выдавай отказ за поломку скилла.
8. **Архивирование доступно только администратору Redmine.** Команды `archive-project` и `unarchive-project` есть, но обычному ключу инстанс ответит отказом — предпросмотр говорит об этом заранее. Правильный ответ пользователю: это делает администратор через «Администрирование → Проекты».

После создания покажи `projects --instance <имя>`: пользователь должен увидеть проект на своём месте в дереве.

## Разбор зависших задач

Задачи копятся годами: часть выполнена, но не закрыта, часть отложена «до выяснения», часть заведена и забыта. Скилл разбирает их пачками, а решение по каждой принимает пользователь.

```bash
... stale --summary                      # сколько и в каких проектах
... stale --page 1 --size 10             # разбор пачками, от самых старых
... stale --category done --summary      # только завершённые, но не закрытые
... close 123 456 789 --note-file /tmp/note.html --yes
```

Порядок работы:

1. **Сводка.** `stale --summary` показывает, сколько задач и в каких проектах. С этого начинается разговор: закрывать 100 задач вслепую нельзя.
2. **Категории различаются по смыслу**, и это надо проговаривать:
   - *завершены, но не закрыты* — уборка: работа сделана, статус не перевели;
   - *отложены* — пауза по чьему-то решению; среди них бывают почти доделанные, они могут ждать ответа заказчика;
   - *без движения* — заведены и забыты, готовность обычно 0–20%; закрытие означает «делать не будем», и это решение человека, а не скилла.
3. **Пачками по десять.** Показывай `stale --page N` целиком: номер, проект, статус, готовность, списанные часы, срок молчания и описание. К каждой давай свою оценку — закрывать или оставить, — но окончательное слово за пользователем.
4. **Закрытие с комментарием.** `close` без комментария отказывается работать: читатель должен понимать, почему задача закрыта и что делать, если тема ещё жива. Для завершённых и для брошенных тексты разные.
5. **Предупреждай об уведомлениях.** Смена статуса рассылает письма участникам и наблюдателям, в клиентских проектах — заказчику. При закрытии десятков задач это десятки писем; пользователь должен знать об этом до начала, а не после.
6. **Закрытые проекты пропускаются.** Их задачи доступны только для чтения, и `close` сообщает об этом отдельным списком вместо ошибки.
7. **Не всякий статус достижим.** Рабочий процесс Redmine разрешает не все переходы, и на запрещённый API отвечает «200», молча оставляя прежний статус. Скилл проверяет допустимость заранее и сверяет результат после записи — если задача не закрылась, он говорит об этом прямо и перечисляет доступные закрывающие статусы.

Задачи закрытых проектов скрыты и в обычной выдаче `issues` — показать их можно флагом `--include-closed-projects`. Они не мешают работе: проект закрыт, значит задачи и так вне активной отчётности.

## Сделанное по истории git

Репозиторий привязывается к инстансу и проекту Redmine, после чего коммиты за период превращаются в черновик отчёта: куда списать часы и какие задачи завести на работу, которая делалась без задачи.

```bash
... repos list
... repos add --path . --instance ru --project 33solutions --client "33 Решения" --activity "Программирование"
... harvest --repo . --period week --out /tmp/harvest
```

Как работает: коммиты за период группируются в рабочие сессии (разрыв больше `--gap` минут = новый заход), часы считаются по времени между первым и последним коммитом сессии плюс разогрев (`--warmup`, по умолчанию 30 минут). Коммиты с `#NNNN` в сообщении относятся к существующей задаче — она проверяется в Redmine; остальные группируются по теме, и по каждой группе предлагается новая задача с черновиком описания.

Правила работы с этим:

1. **Часы из git — это черновик, а не факт.** Всегда говори это вслух и показывай цифры на проверку. Не списывай автоматически.
2. **Черновики описаний дорабатываются** по редакционному стандарту, а не отправляются как есть: сообщения коммитов написаны для разработчика, а не для заказчика.
3. `--out <каталог>` сохраняет `entries.json` (для `batch`), `plan.json` и описания задач — их правят, а потом отправляют обычным путём с подтверждением.
4. Если репозиторий не привязан — предложи привязку: без неё непонятно, в какой проект и какому клиенту относить работу.
5. `--author me` берёт почту текущего пользователя Redmine; `--author all` — работа всей команды (для сводки по проекту, не для списания за других).

## Ретроспектива: заполнить прошлое

Работа, сделанная месяцы назад и не заведённая в трекер, восстанавливается постфактум. Это нормальная операция, но у неё свои правила — без них история получается неправдоподобной и читается как приписка.

```bash
... backfill-check --project eurobrands --period 2026-07-01..2026-09-22   # где дыры
... hours-prompt --period 2026-07-01..2026-09-22 --threshold 30           # чем их закрыть
... batch --file entries.json                                             # предпросмотр по дням
```

Правила:

1. **Даты задачи — реальные.** `--start` и `--due` ставятся по фактическому периоду работы, а не по сегодняшнему дню: по этим полям потом читают историю.
2. **`created_on` через API не задаётся** — ни при каких флагах, дата создания всегда сегодняшняя. Скажи это вслух при первом же ретроспективном заведении и сразу объясни, где реальный период всё-таки виден: поля начала и срока, даты списаний, текст задачи. Предпросмотр задачи с прошлыми датами печатает это сам.
3. **Списание разносится по дням.** Есть поденная разбивка — записывается по дням, а не одной записью на дату закрытия. 27,3 часа в одной клетке за 3 сентября — это не работа, это отметка; те же часы по пяти дням читаются как работа. Одна запись на период допустима, только когда поденных данных нет, и об огрублении говорится вслух.
4. **Проверка правдоподобия.** Перед отправкой `log` и `batch` считают сумму по каждому календарному дню и предупреждают, если в дне больше 12 часов или дата в будущем. Это предупреждение, а не запрет: решает человек, но молча пропускать нельзя.
5. **Порядок переразноса.** Если запись уже есть и её надо разбить: сначала создать новые, убедиться, что легли, и только потом удалять старую (`delete <entryId> --yes`). Не наоборот — иначе при сбое часы пропадут.
6. **Суммы должны сойтись.** После `batch` скилл сам сверяет сумму по каждой задаче «было → стало» и печатает расхождение. Redmine теряет сотые (1,99 возвращается как 1,98), поэтому допуск растёт с числом записей — расхождением считается только то, что больше него.

**Сам предложи заполнить прошлое.** Если пользователь просит завести задачу или списать часы, а по проекту за прошлые периоды пусто (видно по `backfill-check`), спроси один раз, заполнять ли прошлые периоды, и сразу назови способы: по готовым отчётам, по истории git (`harvest`), по журналам рабочих сессий на машине, где шла работа (`hours-prompt` печатает готовый текст для агента на той машине). Отказался — к вопросу в этой сессии не возвращайся.

Методика восстановления часов по журналам — `references/hours-methodology.md`; она вставляется в промпт целиком. Главное из неё: это **нижняя оценка присутствия**, а не счёт; порог склейки блоков называется в каждом отчёте; рядом с часами всегда стоят число сообщений и число дней; чего в журналах нет — того нет, и это пишется словами «данных нет», а не правдоподобным числом.

## Обновление скилла

Скилл обновляется сам: при старте сессии раз в сутки выполняется перемотка вперёд из репозитория (hook `SessionStart`). Вручную:

```bash
bun ~/.claude/skills/redmine-time/scripts/update.ts            # что нового
bun ~/.claude/skills/redmine-time/scripts/update.ts --apply    # обновиться
```

Локальные правки в папке скилла никогда не затираются: при несохранённых изменениях обновление не применяется и сообщает об этом.

## Проверка перед отправкой

Автоматически проверяется каждый текст: секреты и ключи, строки подключения, платёжные и персональные данные, внутренние адреса и пути, самооговор, оценки людей, обещания без основания, внутренняя экономика. Полный перечень и порядок работы с находками — `references/safety.md`.

```bash
... scan --file draft.html                  # проверить черновик отдельно
... scan --text "…" --audience internal     # мягче: внутренний проект
```

Аудитория по умолчанию — `client` (строгий режим). `--audience internal` ставится только для внутренних проектов компании.

Если сканер нашёл запрет: покажи пользователю находку, объясни риск и предложи исправленную формулировку — не проси разрешения «просто отправить как есть». Если секрет уже отправлен ранее — скажи прямо, что правка комментария не помогает (история Redmine хранит версии) и ключ надо отзывать.

## Настройка

Конфиг `~/.redmine/config.json`, образец — `config.example.json`. Ключ берётся в Redmine: *Моя учётная запись → Ключ доступа к API*; пользователь вписывает его сам. Проверка: `... instances`, затем `... whoami --instance ru`.

Поле `"markup"` в профиле задаёт разметку (`html` на наших инстансах); определить для нового — `... detect-markup --instance <имя>`.

## Выбор инстанса

- Явно назван («в ru», «на .company») → `--instance`.
- Не назван → `default` из конфига. Если задача по номеру не нашлась — проверь второй инстанс, прежде чем говорить «не найдено».
- Для `inbox` и `due` бери `--all-instances`: пользователь думает о своей работе целиком.
- `relations`, `relate`, `unrelate` живут в пределах одного инстанса — `--all-instances` для них не бывает. Задача с другого инстанса связывается только перекрёстной ссылкой: `xref`.

## Сценарии

**Списать часы**
```bash
... log --issue 1234 --hours 2.5 --comment "Правила сопоставления номенклатуры: артикул, единицы, НДС"
... log --issue 1234 --hours 2.5 --comment "…" --yes
```
Часы: `2` · `2.5` · `1h30` · `1:30` · `90m`. Даты: `today` · `yesterday` · `-3` · `2026-09-18` · `18.09`.
Комментарий к записи — что именно сделано и по какому этапу; «доработки», «созвон», «тестирование» не годятся (таблица примеров в `editorial.md`).

**Несколько записей сразу** — `batch --file entries.json`; предпросмотр показывает сумму часов, разбивку по дням и пометки о нечеловеческой нагрузке, а после отправки — сверку по задачам «было → стало».

**Заполнить прошлое** — `backfill-check --project X` показывает, где дыры; `hours-prompt` печатает текст для сбора часов по журналам сессий. Правила — раздел «Ретроспектива».

**Что нового**
```bash
... inbox --all-instances                 # с прошлой отметки
... inbox --all-instances --since -3
... inbox --all-instances --mark          # отметить просмотренным
```
`--mark` ставится только после того, как пользователь действительно прочитал сводку.

**Сроки**
```bash
... due --all-instances                   # просрочено / сегодня / горизонт 14 дней
... due --all-instances --exclude-status "Принята,Выполнена"
```
Просрочки старше 90 дней скрыты (`--stale` покажет). Если выдача забита незакрытыми хвостами со 100% готовности — предложи `--exclude-status`, а не пересказывай их все.

**Отчёты**
```bash
... entries --period week --group issue
... entries --period last-month --group date
... gaps --period week
```

**Связи**
```bash
... relations 25185                                       # зависимости задачи словами
... relate 25194 --to 25197 --type blocks                 # предпросмотр
... relate 25194 --to 25197 --type "блокирует" --yes      # создание
... unrelate 812 --yes                                    # удалить связь
... xref 25185 --instance ru                              # строка-ссылка для другого инстанса
```
Связи Redmine работают только внутри одного инстанса; между инстансами связь — перекрёстная ссылка текстом.

**Задачи**
```bash
... issue 1234 --comments 5
... issues --mine --limit 20
... search "обмен с сайтом"
... comment 1234 --text-file /tmp/comment.html          # предпросмотр
... comment 1234 --text-file /tmp/comment.html --yes    # отправка
... create-issue --project 33solutions --subject "…" --description-file /tmp/d.html --due +7
... update-issue 1234 --status "В работе" --done 60 --note "…"
```
Длинные тексты передавай файлами (`--description-file`, `--text-file`): так не ломается HTML и кавычки. Справочники: `... trackers`, `... statuses`, `... activities`, `... projects`.

## Как отвечать пользователю

- Предпросмотр — дословно. Сводки — по сути: сколько списано, где недобор, что просрочено, что требует ответа.
- Всегда давай номер задачи и ссылку (CLI печатает URL нужного инстанса).
- При двух инстансах помечай, откуда задача.
- `--json` — для собственных расчётов; человеку показывай текстовый вывод.

## Диагностика

- `401` — ключ неверный или отозван: перевыпустить в профиле Redmine.
- `403` — не хватает прав у владельца ключа (закрытый проект, списание за другого, создание проекта, архивирование). Для проектов скилл печатает, какое именно разрешение нужно и кто его выдаёт.
- `404` на всех запросах — REST API выключен: *Администрирование → Настройки → API*.
- `422` — валидация: чаще всего нет вида деятельности (`--activity`, см. `... activities`), дата вне допустимого периода или не заполнено обязательное пользовательское поле проекта. В последнем случае скилл называет поле и флаг, которым оно задаётся; полный набор — `... project-fields`.
- Справочники кэшируются на сутки в `~/.redmine/cache.json`; после изменений в Redmine — `--no-cache`.

Подробности REST API — `references/api.md`. Редакционный стандарт — `references/editorial.md`. Правила проверки текстов — `references/safety.md`. Методика восстановления часов — `references/hours-methodology.md`.
